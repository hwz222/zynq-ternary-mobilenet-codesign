# Design reference

Facts below were checked against the sources in this tree. Where a number comes from a report
that is not in this tree it is marked.

## 1. What runs where

The network takes a 256 x 256 x 3 int8 image and produces 14 joint heatmaps of 64 x 64 (int32, stored with
16 channels).

| stage | engine | size |
|---|---|---|
| backbone, 17 blocks | `twn_fuse_top` (fused streaming accelerator) | block 16 output is 8 x 8 x 320 int8 = 20,480 bytes |
| head, 4 operators | `twn_hd_seq` + `twn_hd_compute` inside the same top | op61, op62, op63: 4x4 stride-2 deconvolutions (8x8x320 to 16x16x32, 16x16x32 to 32x32x32, 32x32x32 to 64x64x32); op64: final 1x1, 32 to 16 channels (14 used) |
| read-out, arg-max | processor (`sw/app/mbv2_fuse_ps.c`) | 262,144 bytes of heatmap per frame |

Backbone block `b`: 1x1 expand, 3x3 depthwise (stride 1 or 2), 1x1 project, plus a residual add when the
block has stride 1 and equal channels (10 of the 17). Block 0 is special: its first stage is a 3x3 stride-2
convolution on the 3-channel image instead of a 1x1 expand. Weights of the backbone are ternary (2-bit codes
with per-channel requantisation); activations are int8; the head weights are int8.

The backbone processes one output row at a time: a row of block `b` is computed as soon as the input rows
it needs exist, so the blocks run as a pipeline in rows, with row buffers on chip and the full tensors in DDR.

## 2. Processor to fabric

| interface | direction | used for |
|---|---|---|
| `M_AXI_HPM0_FPD` (32-bit) through one SmartConnect | processor master | AXI4-Lite: `twn_csr` at 0xA000_0000 (registers, block descriptor table, head tables), `obs_gpio` at 0xA001_0000 (a 32-bit observation word) |
| `S_AXI_HP0_FPD` (128-bit, fabric clock) | fabric master | `ARD` reads block input rows, `AWR` writes block output rows |
| `S_AXI_HP1_FPD` | fabric master | `WF` prefetches the next block's weights (read only) |
| `S_AXI_HP2_FPD` | fabric master | `HRD` reads the head input, `HWR` writes the heatmap |
| `S_AXI_HP3_FPD` | fabric master | `HWF` reads the head weights (read only) |

HP3 exists only with `FUSE_HP3_SPLIT=1`, which `vivado/build.cmd` sets. It adds two writes to the
generated `psu_init` (the width of the fourth port), which is why the FSBL in `linux/` comes from the XSA
of such a build. The accelerator does not use the ACP/HPC ports and has no interrupt line: the processor polls.
All masters are instances of `twn_axi_rd` / `twn_axi_wr`: INCR bursts of up to 256 beats of 16 bytes, never
crossing 4 KB, one burst in flight per master.

## 3. DDR arena

A 256 MB region at 0x6000_0000 is reserved in the device tree (`no-map`, so the processor sees it as
uncached device memory: reads are slow, which is why per-frame processor traffic is kept small). Offsets from
the arena base (`sw/app/mbv2_fuse_ps.c`):

| offset | content |
|---|---|
| 0x000000 | backbone weights, `fuse_weights.bin` (740,992 bytes) |
| 0x100000 | activation slot 0, 0x140000 slot 1 (each 262,144 bytes) |
| 0x180000 | input image, written by the processor each frame |
| 0x400000 | head weights (copied from `model_mbv2_packed.bin`) |
| 0x440000 / 0x450000 | head input slot 0 / slot 1 (each 20,480 bytes used) |
| 0x460000, 0x470000, 0x480000 | head intermediates A1 (op61 output), A2, A3 |
| 0x4C0000, 0x500000 | heatmap box A, box B (262,144 bytes each) |

Block `b` reads slot `(b-1) mod 2` and writes slot `b mod 2`; block 0 reads the input image. The
descriptor table (17 blocks x 16 words, written once at boot to 0xA000_1000) holds the slots, geometry and weight
offsets of every block, generated by `tools/gen_desctab.py`.

## 4. Control sequence

Register map and bit layouts: the header of `rtl/fuse/twn_csr.v` and the arms of its write and read
cases; the matching C constants are in `sw/app/pl_hal_fuse.[ch]`. `CTRL` (0x0000) is asymmetric: written bit 1
clears done, read bit 1 is busy and read bit 2 is done. `HD_CTRL` (0x0100) has the same bit meaning on both
sides.

Per frame, with the head in the fabric and `FUSE_BB2HD=1`:

1. The processor writes the input image to the arena.
2. It starts head(k-1): one write to `HD_CTRL`. Then it clears done, writes `IN` and `OUT` pointers, writes
   `CTRL` start, and polls `CTRL` bit 2 until backbone(k) is done.
3. The head and the backbone run at the same time on different HP ports. The processor then waits for
   `HD_CTRL` done, and a different thread reads heatmap box `(k-1) & 1` and does the arg-max.

`A_BB2HD` (0x0060) makes the last backbone block write to `OUT_PTR + parity * 0x10000`, which are the head's
two input slots, instead of activation slot 0. A head start latches the slot the previous backbone wrote and
the heatmap box with it (op61 reads that slot, op64's output base is offset by `0x40000` for box B). With the
bit clear the fabric behaves as before and the processor copies the 20,480 bytes into both head slots and
re-commits op64 each frame. A collision flag (bit 3) is set if the last block starts writing the slot a
running head was given.

The head's four operators are described by four table rows written once at boot through the head
registers (`HD_IN`, `HD_W`, `HD_OUT`, beats, shape, flags, clamp, then `HD_COMMIT`) and a 256-word requantisation
table; the processor never writes them again when `FUSE_BB2HD=1`.

## 5. On-chip memories

| memory | size | role |
|---|---|---|
| head `lbmem_e`, `lbmem_o` | 2 x (64 b x 1,024) = 2 x 2 RAMB36 | head input rows, split by row parity so a window's two source rows are read in the same cycle |
| head `wbank0..3` | 4 x (64 b x 512) = 4 RAMB36 | head weights of the current operator, one bank per kernel-position pair |
| head `obuf` | 64 b x 1,024 = 2 RAMB36 | head output row before it is written to DDR |
| head `RQTAB` | 32 b x 256 = 1 RAMB18 | requantisation parameters of the four head operators |
| backbone | 145 - 10.5 = 134.5 tiles | activation rings, expand-output buffer, output staging, residual buffer, weight memories (4 regions, widths 256/576/256/448 bits, 8,160 / 240 / 600 / 240 words), scatter and array accumulators |

The head figures were read from the routed design of an earlier build of the same RTL (same 145-tile total as
the release build); the backbone split is the remainder of the 145 tiles. The per-module figures of the release
bitstream are in `results/board_results.json`, entry `resources_bitstream_52b400785924efe0`. (A per-instance split of the backbone from an earlier build's hierarchical
report is not reproduced here.) Block-RAM tile count is set mainly by port width, not by depth.

## 6. Verification structure

| gate | what it compares | where |
|---|---|---|
| `P0` / `P1` | fused-order C reference against the plain integer reference, four fixtures; produces the golden vectors | `golden/p0_fused`, `golden/p1_golden` |
| unit tests | each module against an independent model, with deliberate defects ("break tests") that must fail | `rtl/fuse/sim/run_units.ps1` |
| `run_p5` | all 17 blocks through the real sequencer and arrays, 747,520 values | `rtl/fuse/sim/run_p5.ps1` |
| `tb_fuse_frame` | every byte the accelerator writes to DDR over a whole frame, against the golden output, plus the exact issue-beat count (853,760) | `rtl/fuse/tb`, `run_fuse_axi_boost.ps1` |
| `run_hd_int` | the head through CSR, sequencer, three movers and AXI, byte for byte, plus the BB2HD arms | `rtl/fuse/sim/run_hd_int.ps1` |
| board | four fixtures through the whole system, max abs difference 0 | `board/deploy.sh verify` |

`tools/codeprint.py` hashes a source file without comments, to show that an edit changed no code.

## 7. Assumptions that are hard-wired

Correct for the shipped configuration; not parameters in practice:

- `OCMAX` = 4 is assumed in the requantisation rotation, the weight-fetch beat count and the weight-memory depth
  guards in the descriptor table.
- `twn_dw_pack` is correct only for 8 depthwise lanes and 128-byte rows. `twn_act_gather` needs 4 pixels per group.
- `twn_axi_rd` / `twn_axi_wr` assume 128-bit data (the 4 KB boundary arithmetic).
- Row sizes passed to `twn_act_rd` / `twn_act_wr` must be multiples of the word width, or the reader drops the last
  partial word and the writer waits forever.
- The head's capacity checks (mode-A buffer, type-4 channel count multiple of 4) run in simulation only; the
  hardware accepts a bad descriptor.
- The descriptor table check does not read word 11, so `res_slot == in_slot` is assumed, not checked.
- `twn_rowbuf` rotates banks from `rd_row` combinationally while the data and pad flags are registered: the row
  index must be stable when the data is consumed. It supports at most 3 banks.
