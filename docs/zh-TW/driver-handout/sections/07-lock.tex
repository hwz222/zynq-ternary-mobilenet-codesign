\section{並行控制：兩把 mutex 與獨佔開啟}
\label{sec:lock}

\begin{oneline}
同一時間只有一次 \code{open()} 會成功；在開著的這一份裡，backbone 和 head 各用一把 mutex，同一個引擎的暫存器操作不會被兩個 thread 交錯執行。
\end{oneline}

\begin{before}
v1.0.0 完全沒有鎖，也沒有獨佔：\code{/dev/uio4} 誰都能開、開幾次都可以（第 1 章「原本怎麼做」的 \code{fuse_hal_init()}）。兩個 app 一起跑，就會互相改寫對方的描述子表和位址；兩個引擎該怎麼安排，也完全靠 app 自己遵守順序。
\end{before}

\begin{tech}
\begin{itemize}
\item \code{struct mutex}、\code{mutex_lock_interruptible()}：可以睡眠的鎖；等鎖時被訊號（例如 Ctrl-C）打斷就回傳 \code{-EINTR}。
\item \code{test_and_set_bit()}／\code{clear_bit()}：不可分割（atomic）的位元操作，用來實作「只能開一次」。
\item \code{container_of()}：已知某個欄位的位址，算出包含它的 struct 的位址（第 5 章的 \code{file_to_td()}）。
\item \code{.owner = THIS_MODULE}：檔案開著時 module 不能卸載；\code{suppress_bind_attrs}：不提供 sysfs 的 \code{bind}／\code{unbind}。
\end{itemize}
\end{tech}

\begin{gain}
\begin{itemize}
\item 第二次 \code{open()} 得到 \code{-EBUSY}；裝置開著時、以及關掉之後只剩映射時，\code{rmmod} 都被拒絕（板上測過）。
\item 同一個引擎的一整段暫存器操作（\code{BB_RUN} 的「等閒置、清 done、寫位址、START、等 done」）不會被另一個 thread 插進來。
\item 兩個引擎各一把鎖：兩個 thread 分別驅動兩個引擎時互不阻擋。這是設計上的保證；現在的 app 由同一個 thread 依序驅動兩者，量不出差別（見「踩過的坑」）。
\end{itemize}
\end{gain}

\begin{pit}
\textbf{sysfs 的 unbind 會繞過所有保護。}一開始 \code{bind.sh} 用 \code{/sys/bus/platform/drivers/twn_fuse/unbind} 把裝置交還給 UIO。後來發現 unbind 會直接呼叫 \code{remove()}，\code{devm_} 的 buffer 隨即被釋放，就算還有 app 映射著也一樣，app 之後寫進去的資料會落在已經還給系統的記憶體上（讀程式時發現的風險，沒有實際發生）。修法是 \code{.suppress_bind_attrs = true}（第 1 章的 \code{twn_driver}），拿掉 \code{bind}／\code{unbind}；裝置要離開 driver 只剩 \code{rmmod}，而 \code{rmmod} 在檔案開著或 buffer 映射著時會被拒絕。

\textbf{我先前說錯的一件事。}規劃時我說「整個裝置只用一把鎖，重疊會消失，fps 會掉」。這對這個 app 不成立：\code{HD_START} 一下就返回、鎖跟著釋放，硬體已經在跑；接著 \code{BB_RUN} 拿鎖、等 backbone；最後 \code{HD_WAIT}。三個呼叫來自同一個 thread、依序執行，只用一把鎖硬體照樣重疊。兩把鎖真正的作用，是兩個 thread 分別驅動兩個引擎時，等其中一個不會擋住另一個。
\end{pit}

\subsection{原理}

\textbf{為什麼用 mutex，不用 spinlock。}拿著鎖時 driver 會睡：等中斷時睡在 completion 上，輪詢時睡在 \code{usleep_range} 裡，一等就是好幾 ms。spinlock 拿著時不能睡（等鎖的 CPU 會一直空轉），所以只能用 mutex：等不到鎖的 thread 被排程器換下去，把 CPU 讓給別人。ISR 不拿這兩把鎖，它只清 done 與 \code{complete()}，所以不會有「中斷裡等 mutex」的問題。

\textbf{\code{_interruptible} 與 \code{-ERESTARTSYS}。}一般的 \code{mutex_lock} 等鎖時連 \code{kill} 都叫不醒。\code{mutex_lock_interruptible} 被訊號打斷時回傳 \code{-EINTR}，driver 改回傳 \code{-ERESTARTSYS}：這是 kernel 內部的特殊值，返回 user space 前，kernel 依訊號處理函式有沒有設 \code{SA_RESTART}，決定自動重做這個 ioctl，還是讓 app 收到 \code{EINTR}。

\textbf{為什麼一次只開一次。}描述子表、base 位址、BB2HD 模式都是整顆加速器共用的狀態，兩個 process 同時用就會互相蓋掉。讓整個裝置同一時間只有一次 \code{open()} 成功，比替每個開檔維護一份狀態簡單，也符合「一顆加速器同一時間只跑一個網路」的用法。精確地說，它擋的是第二次 \code{open()}：\code{fork()} 出來的子 process、\code{dup()} 出來的 fd 共用同一個開啟的檔案，不會再經過 \code{twn_open()}。

\textbf{rmmod 為什麼會被拒絕。}\code{misc_open} 取得 driver 的 \code{file_operations} 時，因為 \code{.owner = THIS_MODULE}，會把 module 的參考計數加一，檔案完全關閉時才減回去；\code{mmap} 建立的 VMA 也持有這個檔案。所以只要有人開著裝置或映射著 buffer，\code{rmmod} 回報 \code{Module twn_fuse is in use}。

\subsection{面試會問}

\begin{qa}{你的 driver 怎麼處理並行？為什麼用 mutex 不用 spinlock？}
兩層。第一層是獨佔開啟：\code{open} 用 \code{test_and_set_bit}，同一時間只有一次 open 會成功，因為描述子表和 base 位址是整顆加速器共用的狀態。第二層是 thread：backbone 和 head 各一把 mutex，同一個引擎的一整段暫存器操作不會被插隊，兩個引擎互不阻擋；只讀的 \code{STATUS} 不拿鎖。用 mutex 是因為拿著鎖時我會睡在 completion 或 \code{usleep_range} 上好幾 ms，spinlock 不能睡。我也拿掉了 sysfs 的 unbind，因為它會在 buffer 還被映射時釋放 buffer；卸載只剩 \code{rmmod}，板上測過裝置開著、或只剩映射時都被拒絕。
\end{qa}
