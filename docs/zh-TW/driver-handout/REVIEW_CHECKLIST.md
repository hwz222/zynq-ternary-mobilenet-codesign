# 審稿清單

審稿人以「母語是台灣華語、英文是第二語言、會寫 C 與 RTL、但沒寫過 Linux driver，也沒做過中斷、PetaLinux recipe、
SMMU 的工程師」的角度閱讀。每一項回答「通過／不通過」，不通過要寫出具體位置（章、頁或 tex 行號）與建議改法。

## A. 讀得懂

- [ ] 每一章開頭的「一句話」讀完，就知道這章在講什麼。
- [ ] 每一段先講結論，再講理由；沒有超過三行還看不出重點的段落。
- [ ] 每個英文技術名詞第一次出現時，有一句中文解釋，並收在附錄 A；附錄 A 標的章號就是詳細說明的地方。
- [ ] 沒有未解釋的代號、縮寫或內部名稱（build 代號、開機組代號都在導讀定義）。
- [ ] 全份 8 到 10 小時讀得完，篇幅不超過 100 頁。

## B. 三段式完整

- [ ] 「原本怎麼做」引用了實際程式碼（v1.0.0 的 `3bdd485` 或 driver v1.0 的 `7615324`），框的標題寫對是哪一個，並指出問題在哪一行。
- [ ] 「用了什麼技術」列出實際用到的 kernel API、Yocto 變數、Vivado 命令或 RTL 結構的名稱。
- [ ] 「改善了什麼」是具體、可驗證的改變，並對應到板上紀錄或模擬紀錄；沒量的標「未量測」或「推算」。

## C. 例子是真的、而且是現行版本

- [ ] 程式碼都由 `\snip{}` 從 repo 抽出，標題的檔名與行號和原始檔一致。
- [ ] 沒有 `@ commit` 標記的程式碼框，內容就是現在的 repo；有標記的只出現在「原本怎麼做」或明說是舊版本的地方。
- [ ] 正文描述的程式行為（函式名、參數、回傳值、順序、行號）和抽出的現行程式碼一致，沒有沿用舊版本的說法。
- [ ] 板上與模擬輸出是 `results/raw/` 的實際紀錄，框上方的開機組正確；紀錄的開機檔與正文說的版本相符（例如 v1.1 的機制不能拿開機組 A–D 的紀錄當證據，除非正文寫明那是在舊開機檔上量的）。
- [ ] 說明文字裡提到的數字都能在紀錄裡找到；`numbers.tex` 每個數字的出處行號正確。
- [ ] 比較兩個數字時，寫明兩邊是不是同一組開機檔、同一次開機、同一個程式、同樣的次數；不同就寫出差在哪裡。

## D. 前後一致、沒有重複

- [ ] 同一件事只在一章詳細說明；其他地方只有一句加指向，沒有兩段在講同一件事。
- [ ] 跨章的說法互不矛盾（例如「driver 比 UIO 快多少、為什麼」、「buffer 從哪裡配」、「/dev/mem 擋了什麼」、「中斷或輪詢」在每一章都是同一個答案）。
- [ ] 「第 N 章」的指向都對得上；沒有殘留「第一冊」「第二冊」「第 N 節」這類舊講義的說法。
- [ ] 同一個東西整本用同一個名字（例如 buffer／arena、開機組、bitstream 的稱呼）。
- [ ] 導讀的結果總覽、附錄 B 的 30 秒版本、各章的完整版，數字與結論一致。

## E. 原理正確

- [ ] kernel 行為的描述和 Linux 6.1（`6.1.30-xilinx-v2023.2`）的原始碼一致；有疑問的地方，審稿人要實際去查 kernel source。
- [ ] RTL 的描述和 `rtl/fuse/twn_csr.v`、`rtl/src/twn_axi_rd.v` 一致；中斷是 level 還是 edge、何時拉起、何時放下，要和 RTL 與 ISR 對得上。
- [ ] 不誇大：沒做到的（dt_binding_check、sparse、PL 時脈沒有宣告使用）寫清楚；`/dev/mem` 與 SMMU 的保護範圍寫清楚。
- [ ] timing 數字（WNS、WHS，單位 ns）和建置紀錄一致，並說明比較基準是哪一次建置。

## F. 面試題

- [ ] 每章的面試題在本章有答案，30 秒版本在附錄 B，講得完。
- [ ] 回答裡的每個名詞，前文都解釋過。

## G. 速查與排版

- [ ] 「關鍵函式速查」列出本章所有關鍵函式、檔案與行號。
- [ ] 程式碼沒有超出頁寬，圖表清楚，沒有殘留的「待寫」或紅字「紀錄待補」；沒有大片空白頁（章末除外）。

## H. 用語與隱私

- [ ] 用台灣繁體中文用語（記憶體、程式、介面、預設、檔案），沒有中國大陸用語。
- [ ] 沒有板子的真實密碼（只可出現發佈映像公開的預設密碼）、私人路徑、email、個人資料。
