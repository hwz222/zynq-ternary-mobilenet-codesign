\section{重建 bitstream：timing closure}
\label{sec:timing}

\begin{oneline}
v1.1 改了兩次 RTL：加中斷（第 3 節），再把 AXI 交易改成 Non-secure（第 8 節）。兩次都用出貨時的建置配方重建，在 240 MHz 收斂。第一次 route 完就是 +0.037 ns；第二次只改了幾個常數，placement 卻差了 0.18 ns，route 完是 $-$0.032 ns，靠建置腳本在 route 之後自動跑的 \code{phys_opt_design} 補到 0.000 ns，和 v1.0.0 出貨時的情形一樣。
\end{oneline}

\begin{before}[原本怎麼做（v1.0.0 的 bitstream）]
v1.0.0 的 bitstream（\code{52b400785924efe0}）在 240 MHz 收斂得很勉強：第一次 route 後 WNS（Worst Negative Slack，最差路徑的時間餘裕；負的表示這條路徑來不及）是 $-$0.030 ns，建置腳本自動跑 post-route \code{phys_opt_design}，補到 0.000 ns，完全沒有餘裕。出處：\code{results/board_results.json} 的 \code{timing_bitstream_52b400785924efe0}，報告原文在 \code{results/raw/thesis_model_20261012/timing_impl_fuse_ternpose.rpt}。

這個設計的 LUT 用了 93\%、block RAM 用了 97\%，改一點點 RTL，place \& route 的結果就可能不同。
\end{before}

\begin{tech}
\begin{itemize}
\item \textbf{固定的建置配方}：\code{vivado/build.cmd} 裡的變數，包括 implementation strategy \code{Performance_NetDelay_high}、HP3 拆出獨立的 interconnect、一組 block RAM 的位置限制（pblock）；兩次都沒改。
\item \textbf{post-route 恢復}：\code{build_bd_fuse.tcl} 在 route 之後若 WNS < 0，依序跑三種 \code{phys_opt_design} directive，還不行就重新 route 再跑一次。
\item \textbf{資料路徑檢查}：合成後與 route 後各查一次，25 個資料路徑實例都還在 netlist 裡。
\item \textbf{備案：重現加 ECO}：用同一個 commit 在另一個資料夾重建，確認 Vivado 給出一模一樣的中間結果，準備在已經收斂的設計上只改那幾根常數線（ECO，engineering change order）。這次沒有用到。
\end{itemize}
\end{tech}

\begin{gain}
\begin{itemize}
\item 最終的 bitstream（\code{11b4d88f583b8e23}）收斂：WNS 0.000 ns、WHS +0.008 ns，和 v1.0.0 一樣靠 post-route 恢復。
\item 資源幾乎不變：LUT 44,157（v1.0.0 是 44,057，多 0.2\%），block RAM 145 個、DSP 217 個都相同。
\item 可以從 repo 的原始碼重現：\code{build.cmd} 不需要任何手動步驟。
\end{itemize}
\end{gain}

\subsection{原理}

\textbf{只改常數，為什麼 timing 差這麼多。}place \& route 是一個從某個起點出發的最佳化。netlist 只要有一點不同，起點就不同，結果像換了一個亂數種子。AxPROT 從 0 改成 1 看起來只是常數，但 interconnect 裡若有暫存器存這些位元（這是推論）：資料是 0、reset 也是 0 時，暫存器的輸出永遠是 0，合成時會被當成常數刪掉；資料改成 1 之後，reset 期間輸出 0、之後輸出 1，就不再是常數，必須保留。最終版比第一版多了 76 個 LUT，就是 netlist 確實變了的證據（哪些邏輯變了，沒有逐一比對）。

\textbf{同一份配方，結果為什麼不一樣。}出貨版在 2026-10-11 從乾淨的 clone 重建，第一次 route 一樣是 $-$0.030 ns（\code{board_results.json} 的 \code{rebuilt_from_clone_20261011}），表示同樣的輸入會得到同樣的結果；這次的 S5 也證明了這一點。但輸入一變，結果就在 $-$0.03 到 +0.04 ns 之間跳動。這個設計在 240 MHz 本來就沒有餘裕，所以 post-route 恢復是配方的必要部分，不是偶爾才需要的補救。

\textbf{為什麼 ECO 不會影響 timing。}timing 分析看的是暫存器到暫存器之間的路徑。接到常數的 pin 沒有起點暫存器，不在任何路徑上；把它從接地改接 VCC，只是換一條常數線，其他所有 cell 的位置與繞線都不變。

\textbf{retiming 要再驗一次。}最後一步用了 \code{AlternateFlowWithRetiming}，它會把暫存器搬過組合邏輯。工具保證功能不變，但這是會改變電路結構的最佳化，所以上板後仍然重跑了全部的逐位元比對（第 3、8、10 節的開機組 E）。

\subsection{面試會問}

\begin{qa}{改了 RTL 之後 timing 收不了，你會怎麼做？}
先確定建置配方沒變，差異只來自 RTL。這個設計 LUT 用 93\%、block RAM 用 97\%，在 240 MHz 本來就沒什麼餘裕，所以我的建置腳本在 route 後若 WNS 小於 0，會自動依序跑幾種 \code{phys_opt_design}，還不行就重新 route。這次我改了兩次 RTL：加中斷那次 route 完就是 +0.037 ns；把 AxPROT 從 0 改成 1 那次，只改常數，placement 卻差了 0.18 ns，route 完 $-$0.032 ns，靠恢復步驟補到 0。當時我也準備了備案：先證明 Vivado 對同樣的輸入給出同樣的結果，就能重現上一版收斂的設計，再用 ECO 只改那幾根常數 pin，timing 一點都不會動。最後沒有用到。因為最後一步用了 retiming，上板後我重跑了全部的逐位元比對。
\end{qa}
