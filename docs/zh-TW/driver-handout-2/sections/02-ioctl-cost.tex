\section{ioctl 要花多少時間}
\label{sec:ioctl}

\begin{oneline}
一次 ioctl 的來回是 \ioctlUs{} µs，一幀 backbone 的系統呼叫加參數複製只占 \bbSysUs{} µs，真正的成本是 driver 輪詢等硬體時每幀花掉的 \bbCpuUs{} µs CPU 時間，這是第 3 節改用中斷的理由。
\end{oneline}

\begin{before}[原本怎麼做（第一冊沒有量）]
第一冊說 driver 版本「沒有變慢」，根據的是整條 pipeline 的 fps。driver v1.0 其實已經在 \code{TWN_IOC_BB_RUN} 裡量了 START 到 done 的時間（\code{r.ns}），也把 PL 的 cycle 數一起傳回 user space：
\snip{v10_rns}
但沒有任何程式把這兩個數字和 app 自己量的時間放在一起比，ioctl 本身要多少時間、driver 等硬體的方式浪費多少 CPU，都沒有量。面試時被問「你的 driver 有多少 overhead」，只能回答「fps 沒掉」，說不出數字。
\end{before}

\begin{tech}
\begin{itemize}
\item \textbf{三個時鐘對照}：app 用 \code{clock_gettime(CLOCK_MONOTONIC)} 量 ioctl 前後；driver 在 ioctl 裡用 \code{ktime_get_ns()} 量 START 到 done，放進回傳的結構；PL 自己的 cycle counter 除以 240 MHz。三者的差就是各層的成本。
\item \textbf{\code{getrusage(RUSAGE_SELF)}}：這個 process 用掉的 CPU 時間（user 加 kernel），量輪詢佔用多少 CPU。
\item \textbf{空 ioctl 迴圈}：\code{TWN_IOC_STATUS} 不拿鎖、只讀六個暫存器，連打 100,000 次取平均。
\end{itemize}
\end{tech}

\begin{gain}
\begin{itemize}
\item ioctl 介面本身不是瓶頸：一次來回 \ioctlUs{} µs，一幀的系統呼叫加參數複製 \bbSysUs{} µs，不到幀時間的 0.1\%。
\item 找到真正的成本：輪詢的等待（driver 量的時間比 PL 的 cycle 多 \bbWaitUs{} µs）與 CPU 時間（每幀 \bbCpuUs{} µs，佔幀時間 \bbCpuPct{}\%）。第 3 節在另一次開機（開機組 E）上用同一個程式比較輪詢與中斷：等待從 \pollWaitUs{} µs 降到 \irqWaitUs{} µs，CPU 時間從 \pollCpuUs{} µs 降到 \irqCpuUs{} µs。
\end{itemize}
\end{gain}

\subsection{原理}

\textbf{一次 ioctl 經過哪些地方。}app 呼叫 \code{ioctl()}，C 函式庫執行 \code{svc} 指令進入 kernel；kernel 的 \code{sys_ioctl} 用檔案描述子找到 \code{struct file}，呼叫 driver 的 \code{unlocked_ioctl}，也就是 \code{twn_ioctl()}；\code{twn_status()} 讀六個暫存器，\code{copy_to_user()} 把 32 bytes 的 \code{struct twn_status} 寫回，再從 kernel 返回。整條路 1.6 µs，其中六次暫存器讀取各要經過 AXI 到 PL 再回來。

\textbf{為什麼「等待」不全是 driver 的錯。}PL 的 cycle counter 只數 17 個 block 執行的時間，block 和 block 之間的空檔不算（第一冊第 8 節）。所以「driver $-$ PL」裡有一部分是 PL 自己的空檔；它是 driver 叫醒延遲的上限，不是精確值。第 3 節在開機組 E 上同一次開機、同一個程式比較：輪詢時這個差是 \pollWaitUs{} µs，換成中斷後是 \irqWaitUs{} µs，降下來的部分才確定是輪詢造成的。這裡的 \bbWaitUs{} µs 是開機組 D（v1.0.0 的 bitstream 與 kernel）量的，和第 3 節不是同一次開機、同一顆 bitstream，不能直接相減。

\textbf{為什麼輪詢會吃 CPU。}\code{readl_poll_timeout()} 每次睡 13 到 50 µs，用的是高精度計時器（hrtimer）。這個範圍的上限是計時器的硬到期時間，CPU 沒有其他事時多半睡滿 50 µs 才醒，所以一幀 4.13 ms 大約醒來 80 次（估計，沒有量）。每次都要經過計時器中斷、排程器、切回這個 process、讀一次暫存器、再睡，每次只花幾 µs，累積起來每幀約 0.45 ms。

\textbf{量測本身的誤差與範圍。}兩次 \code{clock_gettime} 本身也要時間，但它被平均到 100,000 次裡；\code{getrusage} 的解析度是 µs，總量是 0.45 秒等級，誤差可以忽略。\code{getrusage} 只算這個 process 的 user 與 kernel 時間：這顆 kernel 沒有開 \code{IRQ_TIME_ACCOUNTING}，CPU 閒置時進來的中斷（包括第 3 節的 ISR 與 hrtimer 的中斷）算在 idle，不算在這個 process 上。輪詢時的「等待」在不同開機組、不同設定之間量到 29.2 到 40.0 µs（\code{D2_bench.log} 第 9、18 行，\code{E3_bench.log} 與 \code{G3_bench.log} 第 22 行）；同一設定重複執行的變化沒有量。所以只比較同一次開機、同一個程式的數字。

\subsection{面試會問}

\begin{qa}{你的 driver 有多少 overhead？}
我分三層量。空的 ioctl 一次來回 1.6 µs。跑一幀時，app 量到的時間只比 driver 在 kernel 裡量到的多 3.5 µs，這是系統呼叫加 \code{copy_from_user} 和 \code{copy_to_user}，不到幀時間的 0.1\%。driver 量到的又比 PL 自己數的 cycle 多約 30 到 40 µs，這是輪詢的粒度加上 PL 在 block 之間的空檔；而且輪詢讓這個 process 每幀用掉 0.45 ms 的 CPU，大約 11\%。所以介面不是問題，問題是等待的方式。我改成中斷之後，在同一次開機上用 module parameter 切換比較：CPU 時間從每幀 \pollCpuUs{} µs 降到 \irqCpuUs{} µs，等待從 \pollWaitUs{} µs 降到 \irqWaitUs{} µs。
\end{qa}
