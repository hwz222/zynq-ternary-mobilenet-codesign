\section{發佈 v1.1}
\label{sec:release}

\begin{oneline}
v1.1 的發佈檔可以直接開機使用：root file system 帶著公開、但建置時就設成過期的預設密碼，另附四張不含人物的合成 fixture 與板上工具包，拿到板子的人不需要 PetaLinux、交叉編譯器或 MPII 資料集就能驗證加速器。
\end{oneline}

\begin{before}[原本怎麼做（v1.0.0 的發佈）]
v1.0.0 沒有附 root file system（rootfs，開機後掛成根目錄的整個檔案系統），因為建好的映像裡有板子的 root 密碼雜湊（\code{/etc/shadow}）；也沒有附 fixture，因為四張 fixture 都是 MPII（一個人體姿態資料集）的人物照片，不能再散布。想在板子上驗證，得自己用 PetaLinux 建 rootfs、自己下載 MPII 重新產生 fixture、自己用 SDK 交叉編譯 app。
\end{before}

\begin{tech}
\begin{itemize}
\item \textbf{公開的預設密碼}：\code{build_linux.sh} 沒有給 \code{BOARD_PW} 時，用 \code{twn-v1.1}，雜湊用 \code{openssl passwd -6}（SHA-512 crypt）算好，經 Yocto 的 \code{EXTRA_USERS_PARAMS} 寫進映像。
\item \textbf{密碼一開始就過期}：同一個變數裡的 \code{passwd-expire root} 把 \code{/etc/shadow} 裡 root 的「上次修改日」設成 0。登入時 PAM 的帳號檢查看到它，就要求先改密碼；PetaLinux 對自己的 \code{petalinux} 使用者也是這樣做。
\item \textbf{合成 fixture}：用公式畫出四張圖（漸層、棋盤加圓、條紋、平滑雜訊），標準答案由與加速器逐位元相同的整數參考模型算出。
\item \textbf{板上工具包}（\code{board/make_kit.sh}）：driver 版的 app、測試程式、權重、合成 fixture 打成一個 tar 檔，附 \code{SHA256SUMS}。
\end{itemize}
\end{tech}

\begin{gain}
\begin{itemize}
\item 開機即用：把開機檔放上 SD 卡、開機、登入並改密碼、解開工具包，\code{sh board_check.sh} 就能得到 \code{BOARD CHECK: PASS}（發佈的映像與工具包在開機組 H 驗過：\code{H0_kit_sha.log}、\code{H4_board_check.log}）。
\item 發佈檔裡沒有個人資料：映像只有公開預設密碼的雜湊；fixture 不含任何人物。
\item 預設密碼不能被留著用：序列埠或 ssh 的第一次登入都要先改密碼；改之前，用 ssh 直接執行指令、用 scp 傳檔都被拒絕（開機組 H 實測）。限制：rootfs 是 initramfs，重開機會回到過期的預設密碼。
\end{itemize}
\end{gain}

\begin{pit}
\textbf{第一版的強制改密碼有漏洞。}第一版（開機組 E）不讓密碼過期，而是在 \code{/etc/profile.d/} 放一個腳本：互動式 root 登入時先執行 \code{passwd}，改成功前不給 shell（\code{E7_first_login.log}）。審稿時發現它只攔得住「互動的登入 shell」：\code{ssh root@板子 指令}、\code{scp} 都不經過 \code{profile.d}，拿公開的預設密碼就能以 root 執行任何指令。開機組 E 的 E1--E6 本身就是在第一次互動登入（E7）之前、用預設密碼經 ssh 跑的。改成讓密碼過期之後，檢查發生在 PAM 的帳號檢查，所有登入方式都要經過它，腳本就拿掉了。
\end{pit}

\begin{pit}
\textbf{工具包裡的建置路徑。}發佈前掃描發佈檔時，發現工具包裡兩個 app 的執行檔帶著建置機器上的路徑：它們沒有 strip，debug 資訊裡記著編譯器、SDK 與原始碼的絕對路徑。發佈的其他檔案（BOOT.BIN、bitstream、XSA、kernel、兩個 dtb、boot.scr、rootfs 的 2,513 個檔案、權重與模型檔）都沒有這個問題：\code{tools/scan_release_paths.py} 對發佈檔逐一掃描，找到 0 處，同一個工具對 strip 之前的 app 找到 8 處（\code{S7_release_path_scan.log}）。修法是 \code{board/make_kit.sh} 用 SDK 的 \code{strip} 去掉符號與 debug 資訊，打包後再掃一次，任何檔案含有建置路徑就中止。去掉 debug 資訊不改變程式碼，但檔案的雜湊變了，所以工具包重新在板上驗過（開機組 E 的 \code{E9_release_kit.log}，發佈的版本在開機組 H）。
\end{pit}

\subsection{原理}

\textbf{為什麼映像裡不能放真正的密碼。}\code{/etc/shadow} 存的是雜湊，但雜湊可以離線暴力破解；而且同一份映像會被很多人使用，等於大家共用一組密碼。公開預設密碼加上第一次登入強制修改，是嵌入式產品常見的做法：密碼本來就是公開的，安全性來自「第一次登入的人一定要改掉」。反過來說，在改掉之前，誰先登入誰就能設定密碼，所以第一次開機要在自己控制的網路上。

\textbf{過期的密碼怎麼擋住所有登入方式。}\code{/etc/shadow} 每一列的第 3 欄是上次修改密碼的日期（1970 年起的天數），0 的意思是「必須在下次登入時修改」。序列埠的 \code{login} 與 sshd 都用 PAM 檢查帳號，PAM 的 \code{pam_unix} 看到 0 就回報「需要新密碼」：\code{login} 接著要求改密碼，不改就結束；sshd 在有終端機時同樣要求改，沒有終端機（直接執行指令、scp、sftp（以 ssh 為底的檔案傳輸））就印出 \code{Password change required but no TTY available} 並結束連線。檢查發生在登入的那一刻，和之後執行的是哪一種 shell 無關，這是它比 \code{profile.d} 腳本可靠的原因。

\textbf{initramfs 的副作用。}這個映像的 root file system 是開機時載入記憶體的 initramfs，改的密碼只存在記憶體裡，重開機就回到過期的預設密碼，下一次登入又會被要求修改。要保存，得把 root file system 放到 SD 卡的分割區上；這次沒有做。

\textbf{為什麼合成圖也能當驗證。}驗證的目標是「PL 的計算和參考模型逐位元相同」，不是「姿態估得準不準」。任何輸入都會走過全部 65 個 operator，只要每個 operator 的輸出逐位元相同，用什麼圖都可以。四張圖分別有平滑區、尖銳邊緣、週期圖樣和雜訊，讓數值範圍盡量分散。

\subsection{面試會問}

\begin{qa}{你的發佈映像怎麼處理 root 密碼？}
我不在映像裡放任何真正的密碼。建置腳本沒有給密碼時，用公開的預設密碼，雜湊用 \code{openssl passwd -6} 算好、經 Yocto 的 \code{EXTRA_USERS_PARAMS} 寫進去，同一行再用 \code{passwd-expire} 讓它一開始就過期。這樣序列埠的 \code{login} 和 ssh 的第一次登入都會先要求改密碼；在改掉之前，用 ssh 直接執行指令或 scp 會被拒絕。我在板上實際試過：ssh 帶指令與 scp 都回「Password change required but no TTY available」；序列埠上按 Ctrl-C 會回到登入提示，空密碼和兩次不一致都被拒絕，改完才拿到 shell。第一版我用的是 \code{profile.d} 腳本，審稿時發現它擋不住非互動的 ssh，才改成讓密碼過期。限制是 rootfs 是 initramfs，重開機會回到過期的預設密碼。測試輸入也換成公式產生的合成圖，所以整個發佈檔沒有個人資料。
\end{qa}
