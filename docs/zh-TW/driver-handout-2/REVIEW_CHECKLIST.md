# 審稿清單（第二冊）

審稿人以「母語是台灣華語、英文是第二語言、會寫 C 與 RTL、讀過第一冊、但沒做過中斷、PetaLinux recipe、
SMMU 的工程師」的角度閱讀。每一項回答「通過／不通過」，不通過要寫出具體位置與建議改法。

## A. 讀得懂

- [ ] 每一節開頭的「一句話」讀完，就知道這節在講什麼。
- [ ] 每一段先講結論，再講理由；沒有超過三行還看不出重點的段落。
- [ ] 每個英文技術名詞第一次出現時，有一句中文解釋，並收在附錄 A；第一冊解釋過的可以只附「見第一冊第 N 節」。
- [ ] 沒有未解釋的代號、縮寫或內部名稱（build 代號、開機組代號都要就地定義）。
- [ ] 全份一天（8 小時）內讀得完，篇幅不超過 75 頁。

## B. 三段式完整

- [ ] 「原本怎麼做」引用了實際程式碼（driver v1.0 的 commit `7615324`，或 v1.0.0 的 UIO 寫法），並指出問題在哪一行。
- [ ] 「用了什麼技術」列出實際用到的 kernel API、Yocto 變數、Vivado 命令或 RTL 結構的名稱。
- [ ] 「改善了什麼」是具體、可驗證的改變，並對應到板上輸出或模擬紀錄；沒量的標「未量測」。

## C. 例子是真的

- [ ] 程式碼都由 `\snip{}` 從 repo 抽出，標題的檔名與行號和原始檔一致。
- [ ] 板上與模擬輸出是 `results/raw/linux_driver_v11_20261027/` 的實際紀錄，註明日期與開機檔的雜湊。
- [ ] 說明文字裡提到的函式名、暫存器名、數字，都能在程式碼或紀錄裡找到；`numbers.tex` 每個數字的出處行號正確。
- [ ] 比較兩個數字時，寫明兩邊是不是同一顆 bitstream、同一次開機、同一個程式、同樣的次數；不同就寫「不可比」。

## D. 原理正確

- [ ] kernel 行為的描述和 Linux 6.1（`6.1.30-xilinx-v2023.2`）的原始碼一致；有疑問的地方，審稿人要實際去查 kernel source。
- [ ] RTL 的描述和 `rtl/fuse/twn_csr.v` 一致；中斷是 level 還是 edge、何時拉起、何時放下，要和 RTL 與 ISR 對得上。
- [ ] 不誇大：沒做到的（例如沒有 dtschema 時 binding 只做了部分檢查、sparse 沒跑）寫清楚；SMMU 的保護範圍寫清楚。
- [ ] timing 數字（WNS、WHS，單位 ns）和建置紀錄一致，並說明比較基準是哪一次建置。
